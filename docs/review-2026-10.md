# Application review — October 2026

A review of the whole repository at the end of P18, before production hardening (P19)
begins. It says what the product is, where it actually stands, what was found and fixed,
and what the next version should take on.

---

## What Integr8 Plus is

A multi-tenant field operations platform sold to trade companies on subscription. A
company signs up, builds the forms its engineers fill, and runs its jobs through them:

- **A form engine** (`@integr8/form-engine`): an admin builds a form with pages, sections,
  conditional logic, calculations and repeating groups on the desktop; publishing freezes a
  version; every submission records the version it answered. The same pure engine runs on
  the server, the desktop and the phone, and a conformance corpus proves it produces
  identical bytes in Node and in Hermes.
- **Operations**: customers, sites with access notes and geocoding, job types, work orders
  with a state machine, crews, checklists, comments, photos, sign-off and timesheets.
- **An offline-first mobile app** (Expo): the phone mirrors the engineer's work in SQLite
  behind SQLCipher, every change goes through a transactional outbox, uploads resume after
  the app is killed, and two devices editing the same record produce a resolvable conflict.
- **Platform operations**: a super admin dashboard with separate credentials and a second
  factor, impersonation with an undeletable audit trail, feature flags, announcements,
  company export, scheduled deletion, a global template library and a signup funnel.
- **Metering and billing**: one R2 bucket per company so storage is measurable; seats,
  submissions and storage enforced by the API; a provider-agnostic billing layer with a
  Stripe adapter; trial, dunning and read-only mode.
- **Self-serve onboarding**: landing, features and pricing pages, verify-then-provision
  signup, a computed first-run checklist, demo data, starter templates, a help centre.

It is a pnpm/turbo monorepo: a Fastify API (`apps/api`), a Next.js web app, a Vite + Tauri
desktop app, an Expo mobile app, and thirteen shared packages. About 149k lines of
TypeScript, 119 test files, 18 migrations, 147 OpenAPI operations with a generated client.

## Where it stands

Phases P01–P18 are built. Only P01 and P08 are marked complete, and that is honest: the
others are "built and verified off-device" and wait on something no test can supply — a
real Cloudflare account, Stripe keys, a Supabase project in CI, a phone in a basement, a
person with a stopwatch. P19 (production hardening), P20 (packaging and release) and P21
(first customer) have not started. Nothing has been deployed.

What the automated checks say, on this branch, before any change:

| Check                                    | Result                                           |
| ---------------------------------------- | ------------------------------------------------ |
| `pnpm format:check`, `lint`, `typecheck` | Pass                                             |
| `pnpm build` (18 projects)               | Pass                                             |
| `pnpm test` (unit, no database)          | **One real failure** in the form engine (below)  |
| OpenAPI spec and generated client        | In sync                                          |
| Database, auth and API integration       | Pass against a local Postgres 16, except one (†) |

The CI `database` job is gated on a repository variable that is not set, so **the
isolation, authentication and API suites have never run in CI**. They pass locally; that
is not the same thing.

(†) `sync.integration.test.ts` › "stores identical answers, whichever filled it" reports
`partial` where it expects `complete`, on this branch before and after every change here,
against local-disk media storage. It needs a look on a machine with the real setup; it is
listed under what the next version should take on.

## What the review found

The code is unusually well reasoned: small files, comments that record decisions and
past bugs, tenant isolation defended three ways and each tested with the others off,
strict schemas, a conformance corpus, honest plan files. No route or repository was found
that reads or writes another company's data or trusts a client-supplied tenant id. No
token is stored where a script can read it. The webhook verifies signatures over raw
bytes in constant time.

The defects cluster where two mechanisms meet — a service composing primitives that are
each correct alone — and in error paths written for the happy case.

### Fixed in this branch

Each fix carries a regression test. The integration tests were run against a local
Postgres; the unit suites, lint, typecheck and build pass.

| Area        | Defect                                                                                                                                                                                                                                   | Fix                                                                                                                                                    |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| Form engine | `checkPattern` accepted `[\[--]`, which the regex engine refuses ("range out of order"). `pnpm test` was red. An escaped literal was not treated as the start of a range.                                                                | `pattern.ts` reads an escaped literal as a range start. Property tests get a 60s timeout for loaded CI runners.                                        |
| Auth        | **An impersonating super admin could escape the grant.** `POST /v1/auth/switch-tenant` issued a plain 90-day session in any other company the target belonged to, with no grant, no audit marker, and nothing `end()` could revoke.      | `switchTenant` refuses an impersonated principal (`auth.impersonation_denied`).                                                                        |
| Billing     | **A webhook whose handler threw was lost for ever.** The event row is written before the handler runs; the provider's retry then hit the duplicate branch and did nothing. A paid invoice could leave a company read-only.               | A duplicate that was never applied (error set, or never marked processed) is applied on retry.                                                         |
| Billing     | The portal route built a relative return URL when none was configured and failed with a 500.                                                                                                                                             | Answers 503 `billing_not_configured`, as checkout does.                                                                                                |
| Signup      | `/v1/signup/resend` had no limit and renewed the expiry each time: unlimited mail from our domain to any address somebody typed in.                                                                                                      | Migration 0019 adds `resend_count`; three resends per request, counted in the same statement that rotates the token; the expiry is no longer extended. |
| Signup      | The self-serve owner's password bypassed the policy invited engineers meet (one character was accepted).                                                                                                                                 | `verifySignup` applies the same `assessPassword` before anything is created.                                                                           |
| Members     | An admin could demote, suspend or remove an owner so long as another owner remained.                                                                                                                                                     | Every member action refuses a target ranked above the caller (403).                                                                                    |
| Jobs        | The "claim by the database's clock" fix was bypassed by its only production caller: the worker always passed its own `now`.                                                                                                              | The worker passes a clock only when a test injected one.                                                                                               |
| Jobs        | `complete`/`fail` were not fenced to the lease holder; a slow worker could mark a reclaimed job succeeded or hand it to a third worker. Exhaustion was read-then-write.                                                                  | Both take the worker id and only touch a row still locked by it; exhaustion is decided inside the update; a lost lease is reported as `lost`.          |
| Offline     | **A completion could be stranded for ever.** It waits on other changes by id; resolving a conflict reissues the change under a new id, and deleting a superseded autosave or photo removes the id, so the wait could never be satisfied. | `reissue` rewrites `waits_for` in every waiting row; an id no longer on the phone is not waited for.                                                   |

### Found, not fixed — for the next version

Ranked by what it would cost a real customer. Each needs either a schema change, a design
decision, or a device to verify on.

1. **Offline: a server-side auto-merge is not reflected on the phone.** When two devices
   edit different questions, the server merges and returns the merged answers, but the
   phone keeps its stale copy and the open form state; the next autosave sends the full
   stale set and silently reverts the other device's edit. The merge-then-keep-editing path
   has no test. (`packages/offline/src/sync/outbox.ts` `applyPushResults`;
   `apps/mobile/app/forms/[id].tsx`.)
2. **Offline: a refused or discarded submit leaves the phone showing a submitted form the
   server does not have**, and a permanently failed upload strands the submit that names
   it with no way out but "retry", which fails again. Needs the refresh path to re-fetch
   submissions and the sync screen to offer a way to reopen or discard.
3. **Billing: event ordering.** Stripe does not order deliveries. `customer.subscription.*`
   and `invoice.paid` arriving before `checkout.session.completed` cannot be matched to a
   company and are dropped; the company stays on `trial` and dunning later makes a paying
   customer read-only. `translate` should read the `tenant_id` metadata our own checkout
   sets, and `findTenant` should use it.
4. **Signup: the claim comes after provisioning.** Two concurrent verifies both pass the
   `pending` check; with the real identity provider the second fails with a 502 and the
   request stays pending, so an address that already has a Supabase identity can never
   complete signup. Claim first (`pending` → `verifying`), then provision; look an existing
   identity up instead of failing.
5. **Auth: sign-in lockout is read-then-write.** Concurrent wrong-password attempts never
   reach the threshold; the platform-user version is already atomic and shows the SQL.
6. **Auth: a platform TOTP code can be replayed within its window.** Needs a
   `totp_last_step` column and a check in `signIn`.
7. **Auth: impersonation sessions outlive their grant** (90-day session, 1-hour grant) and
   keep refreshing; the API refuses them per request so this is contained, but the
   documentation says otherwise. Cap `expiresAt` at the grant's and check liveness on
   refresh.
8. **Auth: invitation acceptance always creates a new identity**, so anyone who already
   has one (another company, or re-invited after removal) cannot accept; the fake provider
   hides this because it returns the existing identity where GoTrue returns 422. The
   uniqueness constraints on `tenant_users` are not partial on `deleted_at`, so a
   re-invite after removal fails at accept.
9. **Media: concurrent upload intents bypass the storage quota.** Pending intents are not
   counted and `complete` never re-checks.
10. **API: idempotency keys are tenant-scoped, not user-scoped**, so one user can replay
    another's stored response by reusing their key.
11. **API: `trustProxy: true` unconditionally**; anyone reaching the API directly can spoof
    `X-Forwarded-For` and defeat the per-IP limiter and lockout.
12. **Form engine seams:** a number answer cannot be cleared (the widgets send `''`, which
    the engine refuses for number fields, so the previous value is kept and submitted —
    web, desktop preview and mobile); `readOnly` + `required` with no default publishes a
    form nobody can submit; the submission detail view omits date-relative fields because
    `today` is not supplied on read-back; renaming a question orphans `repeat.titleField`;
    the builder preview stops accepting input after a successful check; the form detail
    cache is stale after publishing.
13. **"Signed out everywhere" does not end an access token** for up to fifteen minutes
    (documented, but a per-request membership check is the real fix, and a decision).
14. **Schema-invariant checks are weaker than they read**: the composite-FK check does not
    confirm the parent column is `tenant_id`, and the RLS check inspects only `qual`. No
    current migration violates either.
15. **One API integration test fails locally** (the P13 phone-and-desktop answers test,
    `partial` instead of `complete`), independent of the changes in this branch. Whether
    it is the local-disk media adapter or a real engine problem is the first thing to find
    out once the suite runs in CI.
16. **Smaller web items:** server-supplied strings and a few literals reach the screen
    outside `@integr8/i18n`; route handlers assume JSON from upstream; the desktop release
    CSP still allows `http://localhost:3000`.

## What the next version should improve

In order. The first three are prerequisites for the first paying customer; the rest are
what the review suggests P19 should contain beyond its current checklist.

1. **Run the integration suites in CI.** Set `DATABASE_TESTS=enabled` with a disposable
   Supabase project. Until then the isolation suite — the most consequential code in the
   repository — has never run anywhere but a laptop. This is step 8 of the Supabase runbook
   and it is overdue.
2. **The real runs the plan files are waiting on**: R2 (P09, P15, P16), Stripe with test
   keys (P17), and a phone in aeroplane mode through the P11–P14 device checklist. Several
   of the findings above (webhook ordering, GoTrue's 422 on duplicate identities) are
   exactly the kind of thing the fakes cannot show.
3. **Fix items 1–4 in the list above** before any engineer uses the app for a day: two of
   them lose field data silently, one can make a paying customer read-only, one locks an
   address out of signup.
4. **Concurrency tests.** Every integration suite is sequential and single-process. The
   lockout counter, the lease fence, signup's claim and the quota check are all races that
   a `Promise.all` of two requests would have exposed.
5. **Make the fakes as strict as the real thing.** `FakeIdentityProvider` should return 422
   for a duplicate email and a short password, as GoTrue does; the recording billing
   provider should deliver events out of order in at least one test.
6. **Finish P18's honest gaps**: the logo upload screen, a billing page that surfaces
   invoices rather than linking out, marketing copy owned by someone, and the
   thirty-minute landing-to-first-submission measurement.
7. **Observability before customers**: the plan has Sentry; it does not yet have a
   dashboard for the funnel, sync failures per device and webhook outcomes, which are the
   three things the review found failing quietly.
8. **Then P19–P21 as planned**: hardening, signed builds, the first customer.

## How this review was done

Static review of every app and package by area (API, database and auth, form engine,
offline and mobile, web and desktop), with each candidate finding verified against the
code path before it was kept. The repository's own checks (`format:check`, `lint`,
`typecheck`, `test`, `build`, OpenAPI drift) were run as CI runs them. The database, auth
and API integration suites were run against a local Postgres 16 with the roles the runbook
describes. Fixes were made only where the defect was confirmed, the change was small and
local, and a regression test could be written; everything else is listed above with a file
to start from.
